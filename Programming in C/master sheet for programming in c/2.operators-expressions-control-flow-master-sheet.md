### 1. THE 30-SECOND BIG PICTURE (Prime + Dual Coding)

* **1-Sentence Core Idea (Feynman):** C evaluates any program by first grouping tokens into a syntax tree (precedence/associativity), then executing sub-expressions only when sequence points and short-circuit rules permit, and finally steering execution through strict branch and loop jump rules.
* **Master Map:**

```text
                  [ C PROGRAM EXECUTION (GATE CORE) ]
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼                                                 ▼
[ 1. EXPRESSIONS ]                                [ 2. CONTROL FLOW ]
  ├─ Grouping (Parse Tree)                          ├─ Branching
  │   ├─ Precedence (Postfix > Unary > Binary)      │   ├─ if-else (Nearest unmatched if)
  │   └─ Associativity (R->L: Unary, ?:, Assign)    │   └─ switch (Int const, fall-through, default anywhere)
  ├─ Evaluation Control                             └─ Loops & Jumps
  │   ├─ Short-Circuit (&&, || suppress RHS)            ├─ for / while / do-while
  │   ├─ Sequence Points (; && || ?: , call)            ├─ Loop Invariants (Init -> Maint -> Term)
  │   └─ UB (Unsequenced double-write / R+W)            └─ break (exit loop/switch) vs continue (next iter)
  └─ Bit-Level Math
      ├─ Masking (&, |, ^, ~) & Power-of-2
      └─ Shifts (<<, >>): Logical vs Arithmetic (Signed)

```

### 2. COMPLETE COMPRESSED MODULES (Chunked + Active Recall)

#### M1. Precedence, Associativity & Unary vs Binary

* **Cue:** How does C decide which operator binds first, and does precedence dictate execution order?
* **Intuition (Feynman):** Precedence and associativity only draw invisible parentheses around operators; they do **not** decide which side runs first.
* **Mechanics:**
* **Tier Order (High → Low):** Postfix (`()`, `[]`, `->`, `.`, `++`, `--`) → Unary (`++`, `--`, `+`, `-`, `!`, `~`, `(type)`, `*`, `&`, `sizeof`) → Arith (`* / %`, `+ -`) → Shift (`<< >>`) → Rel (`< <= > >=`) → Eq (`== !=`) → Bitwise (`&` → `^` → `|`) → Logical (`&&` → `||`) → Ternary (`?:`) → Assign (`=`, `+=`) → Comma (`,`).
* **Only 3 groups associate Right-to-Left (R→L):** Unary, Ternary (`?:`), and Assignment (`=`). Everything else is Left-to-Right (L→R).
* **Pointer + Unary Combo:** Postfix beats Prefix/Dereference → ``*p++`` parses as ``*(p++)``; same-tier Unary goes R→L → ``*++p`` is ``*(++p)`` and ``++*p`` is ``++(*p)``.


* **Example:** `int a[] = {10, 20}, *p = a; int x = *p++;` → dereferences old `p` (`x = 10`), then advances `p` to `20`.
* **Trap / Edge Case:** Precedence != evaluation order: in `f() + g() * h()`, `*` groups `g()` and `h()`, but `f()` may still execute before `g()` or `h()`.

#### M2. `sizeof`, Comma (`,`) & Type Conversions

* **Cue:** When are operands skipped completely, and what does the comma operator actually return?
* **Intuition (Feynman):** `sizeof` inspects only the type blueprint at compile time, while `,` runs the left side for effects and hands back the right side.
* **Mechanics:**
* **`sizeof(expr)`:** Resolved at compile time → operand is **never evaluated** → all side effects inside (`++`, `=`) are ignored (sole exception: C99 Variable Length Arrays).
* **Comma Operator (`e1, e2`):** Lowest precedence (below `=`) → evaluates `e1`, discards it, hits a sequence point, evaluates and returns `e2`.
* **Integer Promotion:** `char`/`short` promote to `int` in expressions; mixing `int` and `unsigned int` converts the signed value to **unsigned** (negative becomes huge positive).


* **Example:** `int x = 5, y; y = (sizeof(x++), x + 1);` → `x++` does not run → `x` stays `5`, `y` becomes `6`.
* **Trap / Edge Case:** `int a = 1, 2;` fails (separator), and `a = 1, 2;` parses as `(a = 1), 2;` (`a` gets `1`, not `2`); also `(-1 < 1U)` is **false** (`-1` converts to `UINT_MAX`).

#### M3. Short-Circuit Evaluation (`&&`, `||`)

* **Cue:** How do `&&` and `||` suppress side effects in the right-hand operand?
* **Intuition (Feynman):** Once the left side alone locks in the final true/false verdict, C stops dead and refuses to touch the right side.
* **Mechanics:**
* `A && B`: Eval `A` → if `A == 0`, return `0` immediately (`B` skipped); else eval `B` and return `B != 0`.
* `A || B`: Eval `A` → if `A != 0`, return `1` immediately (`B` skipped); else eval `B` and return `B != 0`.
* **Precedence:** `&&` binds tighter than `||` → `A || B && C` parses strictly as `A || (B && C)`.
* **Output Guarantee:** Always produces `int` `0` or `1` (never returns the original truthy operand value like Python/JS).


* **Example:** `int a = 0, b = 1, c = 1; int r = ++a || ++b && ++c;` → `++a` yields `1` → short-circuits entire RHS → `r=1, a=1, b=1, c=1`.
* **Trap / Edge Case:** Confusing `&&` with `&` (or `||` with `|`) — bitwise operators **never** short-circuit and always evaluate both sides.

#### M4. Bitwise Operations (`&`, `|`, `^`, `~`) & Masking Idioms

* **Cue:** How do you inspect, modify, or test binary properties of an integer in O(1) bit ops?
* **Intuition (Feynman):** Bitwise operators apply Boolean logic independently to every matching bit column in parallel.
* **Mechanics:**
* **Bit `k` (0-indexed from LSB):** Check: `(n >> k) & 1` | Set: `n | (1U << k)` | Clear: `n & ~(1U << k)` | Toggle: `n ^ (1U << k)`.
* **Power of 2 & LSB Tricks:** Clear lowest set bit → `n & (n - 1)`; Isolate lowest set bit → `n & -n`; Power of 2 check → `(n > 0) && ((n & (n - 1)) == 0)`.
* **XOR & NOT Identities:** `x ^ x = 0`, `x ^ 0 = x` (cancels duplicates); in 2's complement, `~x == -(x + 1)` (e.g., `~0 == -1`).


* **Example:** `n = 12` (`1100`): `n & (n - 1)` = `1100 & 1011` = `1000` (`8`) → non-zero, so `12` is not a power of 2.
* **Trap / Edge Case:** `==` and `!=` have **higher** precedence than `&`, `^`, `|` → `if (n & 1 == 0)` parses as `n & (1 == 0)` → always false! Always parenthesize `(n & 1) == 0`.

#### M5. Bitwise Shifts (`<<`, `>>`) & Signed Integers

* **Cue:** How do logical and arithmetic right shifts differ on signed vs unsigned numbers, and when do shifts trigger UB?
* **Intuition (Feynman):** Shifting slides bits left (multiply by 2) or right (divide by 2), while signed right shift copies the sign bit to keep negative numbers negative.
* **Mechanics:**
* **Unsigned `<< k` / `>> k`:** Fills vacated bits with `0` (Logical shift) → `x << k` = `(x * 2^k) mod 2^w`; `x >> k` = `floor(x / 2^k)`.
* **Signed `>> k` (negative `x`):** Implementation-defined in C; virtually all CPUs/GATE use **Arithmetic Right Shift** (fills MSB with sign bit `1`, rounds toward `-∞`).
* **Shift UB Triggers:** Shifting by `k < 0` OR `k >= bit_width` → **UB**; Left-shifting a negative signed integer or overflowing into the sign bit → **UB**.


* **Example:** In 8-bit 2's complement, `-5` (`11111011`) `>> 1` = `11111101` (`-3`), whereas `-5 / 2` truncates toward zero to `-2`.
* **Trap / Edge Case:** Assuming `x >> 1` equals `x / 2` for negative odd numbers (it doesn't: `-5 >> 1 == -3`, `-5 / 2 == -2`), or doing `1 << 31` on a 32-bit signed `int` (UB; use `1U << 31`).

#### M6. Sequence Points & Undefined Behaviour (UB)

* **Cue:** When is a C expression illegal (UB) vs compiler-dependent (Unspecified) vs strictly defined?
* **Intuition (Feynman):** A sequence point is a sync barrier; changing a variable twice (or reading and changing it independently) without a barrier between them breaks C's contract.
* **Mechanics:**
* **Exact Sequence Points:** `;` (end of full expr), `&&`, `||`, `?:` (after cond), `,` (comma operator only), function call (after all args, before body), `return`/control expr end.
* **UB Law:** Modifying an object `> 1` time, OR reading and modifying it (unless the read solely computes the new value, like `i = i + 1`), between two sequence points → **Undefined Behaviour**.
* **Unspecified Order:** Order of evaluating sub-expressions (`f() + g()`) or function args (`foo(a(), b())`) has no sequence point between them → valid if disjoint variables, order picked by compiler.


* **Example:** `i = i++ + ++i;` and `a[i] = i++;` and `printf("%d %d", i, i++);` → **UB**. Contrast: `i++ && ++i;` → **Well-defined** (`&&` is a sequence point).
* **Trap / Edge Case:** Function argument commas are **separators**, NOT the comma operator → `foo(i++, i++)` has **no** sequence point between arguments → **UB** (GATE avoids asking for numeric output of UB).

#### M7. Conditional Control Flow (`if-else` Dangling-Else & `switch`)

* **Cue:** How does C resolve unbraced `if-else` nests, and what are the exact jump rules inside `switch`?
* **Intuition (Feynman):** An `else` always grabs the closest available `if` above it regardless of spacing, while `switch` is a one-shot jump table that slides downward until stopped.
* **Mechanics:**
* **Dangling-Else Rule:** Every `else` binds to the **nearest preceding unmatched `if**` in the same `{ }` block; indentation is invisible to the compiler.
* **`switch(expr)` Constraints:** `expr` must be integral (`int`, `char`, `enum`; never `float`/string); `case` labels must be unique **compile-time integer constants** (no variables).
* **Fall-Through & `default`:** Matching a `case` executes every line below it across later `case`/`default` labels until `break`/`return`/`}`. `default` can sit **anywhere** (runs only if no `case` matches, then falls through if no `break`).


* **Example:** `if (0) if (1) x=1; else x=2;` → `else` binds to `if (1)`, so outer `if (0)` skips everything (`x` unchanged).
* **Trap / Edge Case:** Placing `default:` at the top of a `switch` without `break` causes it to fall through into `case 1:` below it; statements placed before the first `case:` are dead code (never executed).

#### M8. Loops (`for`, `while`, `do-while`), Invariants & `break` vs `continue`

* **Cue:** How do loop structures differ on entry/continue, and how do you prove loop correctness with an invariant?
* **Intuition (Feynman):** Loops repeat until a guard fails, `break`/`continue` hijack the jump target, and an invariant is the unbreakable truth that proves the final answer.
* **Mechanics:**
* **Loop Execution:** `while` = entry-controlled (0+ runs); `do-while` = exit-controlled (1+ runs, ends with `;`); `for(init; cond; upd)` = `init` once → `cond` (empty = always `1`) → body → `upd` → `cond`.
* **Loop Invariant Proof (3 steps):** **Initialization** (true before iter 1) → **Maintenance** (true before iter `k` ⇒ true after iter `k`) → **Termination** (`Invariant && !cond` ⇒ desired post-condition).
* **`break` vs `continue`:** `break` exits the **innermost loop OR `switch**`. `continue` skips to the next iteration of the **innermost loop ONLY** (in `for`, jumps to `upd`; in `while`/`do-while`, jumps straight to `cond`).


* **Example:** In `switch` nested inside a `for` loop, `break` exits only the `switch`, whereas `continue` jumps straight to the `for` loop's `upd` step.
* **Trap / Edge Case:** Putting `continue` *before* `i++` inside a `while` loop skips the increment and causes an **infinite loop** (unlike `for`, where `continue` still runs `upd`).

* `Q: What is the safe O(1) check for whether signed int n is a power of 2? | A: (n > 0) && ((n & (n - 1)) == 0).`
* `Q: What is ~x in 2's complement arithmetic? | A: -(x + 1) (e.g., ~0 = -1, ~5 = -6).`
* `Q: Which 3 shift conditions cause Undefined Behaviour in C? | A: Shift count < 0, shift count >= bit-width, or left-shifting a negative/sign-overflowing signed int.`
* `Q: List all expression-level sequence points in C. | A: ; (full expr), &&, ||, ?: (after cond), comma operator (,), and function call entry.`
* `Q: Why is a = 1, 2; different from a = (1, 2);? | A: Comma has lower precedence than =, so a = 1, 2 assigns 1 to a, while a = (1, 2) assigns 2.`
* `Q: What are the 3 pillars of a Loop Invariant proof? | A: Initialization (pre-loop), Maintenance (iter k → k+1), and Termination (Invariant && !cond → post-condition).`
