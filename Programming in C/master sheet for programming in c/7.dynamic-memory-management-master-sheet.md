### 1. THE 30-SECOND BIG PICTURE (Prime + Dual Coding)

* **1-Sentence Core Idea (Feynman):** The Heap is a manual, runtime-sized memory pool where you rent raw byte chunks via `stdlib.h` pointers and must explicitly return every chunk exactly once—losing a receipt leaks RAM, while keeping or misusing an expired receipt corrupts the allocator itself.
* **Master Map:**

```text
               [ DYNAMIC MEMORY MANAGEMENT — HEAP (GATE CORE) ]
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        ▼                             ▼                             ▼
[ 1. HEAP ALLOCATORS ]       [ 2. CLASSIC MEMORY BUGS ]    [ 3. DYNAMIC 2D ARRAYS ]
  ├─ malloc(sz)                ├─ Memory Leak                ├─ Array of Row Ptrs (int **)
  │   (Raw garbage bytes)      │   (Lost ptr, never freed)   │   ├─ R + 1 mallocs & frees
  ├─ calloc(n, sz)             ├─ Dangling Pointer / UAF     │   └─ Jagged OK, non-contiguous
  │   (Zero-initialized)       │   (Use after free / pop)    └─ Single Flat Block
  ├─ realloc(ptr, new_sz)      ├─ Double Free                    ├─ 1 malloc & 1 free
```

### 2. COMPLETE COMPRESSED MODULES (Chunked + Active Recall)

#### M1. Heap Architecture & Allocation (`malloc`, `calloc`)

* **Cue:** How does the Heap differ from the Stack, and what separates `malloc` from `calloc`?
* **Intuition (Feynman):** While the Stack auto-cleans fixed frames when functions exit, the Heap gives you runtime-sized storage that stays alive until you explicitly call `free`—with `malloc` handing you dirty memory and `calloc` wiping it clean first.
* **Mechanics:**
* **Heap Contract (`stdlib.h`):** Allocates contiguous bytes from the Heap segment → returns properly aligned `void *` (implicitly converts to any pointer type in C; returns `NULL` on failure).
* **`malloc(size_t bytes)`:** Reserves `bytes` with **indeterminate (garbage)** contents → fastest allocation (`O(1)` amortized).
* **`calloc(size_t count, size_t elem_sz)`:** Reserves `count * elem_sz` bytes and **zero-initializes every bit to `0x00**` → slightly slower than `malloc`, prevents stale data leaks, and guards multiplication overflow internally.


* **Example:** `int *a = malloc(n * sizeof(*a));` (garbage ints) vs `int *b = calloc(n, sizeof(*b));` (all elements `0`); always check `if (a == NULL)` before dereferencing.
* **Trap / Edge Case:** Calling `malloc(0)` is **implementation-defined** (returns either `NULL` or a unique non-`NULL` pointer you must not dereference, only pass to `free`); also, casting `(int *)malloc(...)` in C is unnecessary and hides a missing `stdlib.h` include.

#### M2. Resizing & Deallocating (`realloc`, `free`)

* **Cue:** How does `realloc` relocate memory without losing data, and what inputs are legal vs fatal for `free`?
* **Intuition (Feynman):** `realloc` tries to expand your room into the vacant space next door, or else rents a bigger room elsewhere, moves your furniture, and cancels the old lease—while `free` hands the keys back to the allocator.
* **Mechanics:**
* **`realloc(ptr, new_sz)`:** Attempts in-place resize → if blocked, allocates `new_sz`, copies `min(old_sz, new_sz)` bytes, frees old `ptr`, and returns the new base address (new bytes are uninitialized).
* **Special `realloc` Rules:** `realloc(NULL, sz)` behaves identically to `malloc(sz)`; on failure, `realloc` returns `NULL` and **leaves the original block intact and allocated**.
* **`free(ptr)`:** Returns the chunk to the allocator's **free-list** for future reuse (does not necessarily return RAM to the OS immediately) → `free(NULL)` is a guaranteed safe **no-op**.


* **Example:** Safe resize pattern: `int *tmp = realloc(p, new_n * sizeof(*p)); if (tmp != NULL) p = tmp;` — preserves `p` if allocation fails.
* **Trap / Edge Case:** Writing `p = realloc(p, big_sz);` directly overwrites `p` with `NULL` on failure, instantly leaking the old block; passing a stack address (`free(&x)`) or offset pointer (`free(p + 1)`) triggers **UB** / heap crash.

#### M3. Memory Leaks & Dangling Pointers (Use-After-Free)

* **Cue:** How do memory leaks and dangling pointers arise, and why is Use-After-Free (UAF) a critical security flaw?
* **Intuition (Feynman):** A memory leak throws away the key to a rented room you still pay for, while a dangling pointer keeps using an old key after the landlord already rented the room to someone else.
* **Mechanics:**
* **Memory Leak Triggers:** Overwriting a heap pointer (`p = malloc(...)` again), returning from a function when a local pointer holding heap RAM goes out of scope, or freeing a parent `struct` before freeing its internal heap fields.
* **Dangling Pointer Triggers:** Accessing `p` after `free(p)` (because `free` never alters `p`'s stored address), or returning `&local_auto` from a function whose stack frame gets popped.
* **Use-After-Free (Security Hook):** Freeing chunk `A`, reallocating the same slot for object `B`, then writing through stale pointer `A` silently hijacks `B`'s data or function pointers.


* **Example:** `int *p = malloc(4); int *q = p; free(p); p = NULL;` → `p` is neutralized, but alias `q` is still a live **dangling pointer** (`*q = 5;` is UAF / UB).
* **Trap / Edge Case:** Assuming `free(p)` sets `p` to `NULL` automatically—C passes `p` **by value** to `free`, so `free` physically cannot modify the caller's pointer variable!

#### M4. Double Free & Heap Buffer Overflow (Corruption Mechanics)

* **Cue:** How do Double Free and Heap Buffer Overflow corrupt the allocator's internal state?
* **Intuition (Feynman):** Allocators scribble hidden bookkeeping notes right next to your data; freeing twice scrambles the ledger into returning one room to two tenants, while overflowing writes straight over the neighbour's bookkeeping.
* **Mechanics:**
* **Chunk Metadata Layout:** Every heap chunk sits adjacent to hidden allocator headers (chunk size, in-use flag bits) and, when freed, inline `fd`/`bk` linked-list pointers (`glibc` bins/tcache).
* **Double Free (`free(p); free(p);`):** Inserts the same chunk into the free-list twice → corrupts bin integrity (**UB** / abort in modern `glibc`), or lets two subsequent `malloc` calls receive the **exact same address** (exploitation primitive).
* **Heap Buffer Overflow:** Writing past allocated byte bounds (`p[n]` on an `n`-element block) overwrites adjacent chunk metadata or neighbouring heap objects → causes crashes or arbitrary memory-write exploits.


* **Example:** `char *s = malloc(strlen(src)); strcpy(s, src);` omits `+ 1` for `'\0'` → off-by-one heap overflow that corrupts the next chunk's size/flag byte!
* **Trap / Edge Case:** Using `sizeof(p)` on a heap-allocated array (`memset(p, 0, sizeof(p))`) only clears `4B`/`8B` (the pointer's size), **not** the allocated block size—always track the byte count in a separate variable.

#### M5. Dynamic 2D Arrays (Row Pointers vs Single Contiguous Block)

* **Cue:** How do the `int **` row-pointer method and the single flat-block method compare in memory layout, indexing, and cleanup?
* **Intuition (Feynman):** You can build a dynamic grid either as a binder of separate page pointers (flexible rows, scattered in RAM) or as one giant contiguous sheet folded mathematically by row width.
* **Mechanics:**
* **Method 1 — Array of Row Pointers (`int **a`):** `a = malloc(R * sizeof(int *));` then loop `a[i] = malloc(C * sizeof(int));` → `R + 1` allocations, supports **jagged rows**, native `a[i][j]`, scattered RAM (cache misses), must `free(a[i])` in a loop **before** `free(a)`.
* **Method 2 — Flat 1D Block (`int *a`):** `a = malloc(R * C * sizeof(int));` → `1` allocation, `1` `free(a)`, 100% contiguous (cache-friendly), manual row-major indexing `a[i * C + j]`.
* **Method 3 — Flat Block with 2D Syntax (`int (*a)[C]`):** `int (*a)[C] = malloc(R * sizeof(*a));` (C99 VLA pointer) → `1` allocation, `1` `free(a)`, contiguous RAM, **and** native `a[i][j]` syntax!


* **Example:** Flat-block cleanup is 1 line (`free(a);`), whereas `int **a` requires `for (int i = 0; i != R; i++) free(a[i]); free(a);`.
* **Trap / Edge Case:** Calling `free(a)` first on an `int **` 2D array loses every row pointer `a[0..R-1]` and leaks all `R` rows instantly; also, `int **a` is **not** guaranteed contiguous across rows.

### 3. CONFUSION-KILLER TABLE (Interleaving)

| Concept | Core Difference | When to Use / Trigger | Common Trap |
| --- | --- | --- | --- |
| **`malloc` vs `calloc**` | `malloc(sz)` leaves garbage bytes; `calloc(n, sz)` zero-fills all bits (`0x00`) and multiplies `n * sz`. | Overwriting entire buffer immediately vs needing clean zeroed arrays/structs. | Assuming `malloc` initializes memory to zero (it only *sometimes* looks zero on fresh OS pages). |
| **`realloc` In-Place vs Relocate** | In-place keeps original address; relocation allocates new block, copies data, and frees old block. | Growing/shrinking dynamic arrays (vectors, buffers). | Keeping old alias pointers `q = p` after `realloc` (they dangle if `realloc` moved the block!). |
| **Memory Leak vs Dangling Pointer** | Leak = allocated block with **0** reachable pointers; Dangling = live pointer to **freed/popped** RAM. | Diagnosing OOM growth vs random crashes / UAF corruption. | Thinking setting `p = NULL` *before* `free(p)` avoids bugs (that actually creates a leak!). |
| **Double Free vs Use-After-Free** | Double Free calls `free(p)` twice (breaks allocator bins); UAF reads/writes `*p` after `free(p)`. | Heap corruption analysis and security audits. | Forgetting that `p = NULL` prevents Double Free on `p`, but fails if another alias `q` is freed. |
| **Stack vs Heap Allocation** | Stack: LIFO, automatic cleanup, small fixed limit, `O(1)` SP shift; Heap: manual `free`, huge, fragmented. | Local variables with short scope vs large/runtime-sized persistent data. | Returning `&local` (stack) instead of returning a `malloc`'d pointer (heap). |
| **`free(NULL)` vs `free(offset)**` | `free(NULL)` is guaranteed safe no-op; `free(p + k)` (`k != 0`) is strict **UB** (corrupts metadata). | Safe cleanup paths vs advancing pointers over heap buffers. | Incrementing `p++` during traversal and passing the shifted `p` directly to `free(p)`. |
| **2D `int **` vs Flat `int *` / `int (*)[C]**` | `int **` uses `R+1` allocs/frees (jagged OK, cache-poor); Flat uses `1` alloc/free (contiguous, cache-fast). | Variable-length string lists vs high-performance matrices/DP tables. | Freeing `a` before `a[i]` in `int **`, or passing `int **` where `int (*)[C]` is expected. |

### 4. RAPID LOCK-IN (Active Recall + Spaced Repetition)

#### 60-Second Self-Test

1. **Leak Bug Hunt:** What exact bug occurs if `realloc` fails inside `p = realloc(p, 1000000);`, and what is the 2-line fix?
2. **Value vs Reference Trap:** After executing `int *p = malloc(sizeof(int)); free(p);`, is `p == NULL` guaranteed to be true? Why or why not?
3. **Alias Dangling Check:** `int *p = malloc(4); int *q = p; free(p); p = NULL; free(q);` — Which exact memory bug does `free(q)` trigger?
4. **Off-By-One Overflow:** Why does `char *dup = malloc(strlen(s)); strcpy(dup, s);` corrupt the heap, and what exact byte does it smash?
5. **Offset Free Bug:** `int *p = malloc(5 * sizeof(int)); p++; free(p);` — Valid or Undefined Behaviour? Explain in 1 line.
6. **2D Free Order:** For a `3 x 4` matrix allocated as `int **a` (using `R + 1` calls to `malloc`), how many total `free()` calls are required, and in what exact order?
7. **`sizeof` Illusion (64-bit, 4B `int`):** `int *a = calloc(100, sizeof(int)); printf("%zu %d", sizeof(a), a[99]);` — What prints?

#### Spaced-Repetition Flashcards (Day 1 / 3 / 7)

* `Q: What is the key behavioural difference between malloc(n * sz) and calloc(n, sz)? | A: malloc leaves bytes uninitialized (garbage); calloc zero-initializes every bit to 0x00.`
* `Q: What does realloc(ptr, new_sz) do if it cannot allocate the requested size? | A: Returns NULL and leaves the original block at ptr untouched and still allocated.`
* `Q: What are the special behaviours of realloc(NULL, sz) and free(NULL)? | A: realloc(NULL, sz) acts like malloc(sz); free(NULL) is a guaranteed safe no-op.`
* `Q: Why can free(p) never set the caller's pointer p to NULL? | A: C passes p by value, so free receives only a copy of the address and cannot mutate caller's p.`
* `Q: What causes a Memory Leak vs a Dangling Pointer? | A: Leak = losing all pointers to unfreed heap RAM; Dangling = keeping a pointer to freed heap or popped stack RAM.`
* `Q: How does a Double Free corrupt a heap allocator at the mechanism level? | A: Inserts the same chunk twice into the free-list/bin, corrupting bin pointers or causing two mallocs to return the same address.`
* `Q: Why is a Heap Buffer Overflow dangerous even if it only overflows by 1 byte? | A: The byte immediately past the buffer is the adjacent chunk's allocator metadata (size/in-use flags), corrupting heap control structures.`
* `Q: How many malloc and free calls does an R x C dynamic 2D array via int **a require? | A: R + 1 mallocs and R + 1 frees (free every row a[i] in a loop first, then free(a) last).`
* `Q: How do you allocate a single contiguous R x C heap matrix that still supports native a[i][j] indexing in C99? | A: int (*a)[C] = malloc(R * sizeof(*a)); (1 malloc, 1 free, contiguous row-major layout).`
* `Q: What happens if you call free(p) after advancing p++ on a malloc'd pointer? | A: Undefined Behaviour (heap corruption/crash); free must receive the exact base address returned by malloc/calloc/realloc.`

#### Answer Key

1. **Memory leak** (`realloc` returns `NULL` without freeing the old block, and assigning directly to `p` destroys the only reference to it). Fix: `int *tmp = realloc(p, 1000000); if (tmp != NULL) p = tmp;`.
2. **No** — `free(p)` receives `p` by value and cannot change it; `p` still holds the old address (now a dangling pointer) unless you manually write `p = NULL;`.
3. **Double Free** (UB / heap corruption) — `q` still points to the already-freed chunk even though `p` was nulled out.
4. `strlen(s)` excludes `'\0'`, so `strcpy` writes `'\0'` 1 byte past the allocated block, smashing the next heap chunk's header metadata.
5. **Undefined Behaviour** — `free()` only accepts the exact base pointer returned by an allocator (or `NULL`), never an interior/offset address.
6. **`4` calls (`R + 1`)** — first `free(a[0])`, `free(a[1])`, `free(a[2])` in any order, and finally `free(a)` last.
7. **`8 0`** (`sizeof(a)` is the 64-bit pointer size `8B`, not `400B`; `calloc` guarantees `a[99] == 0`).
